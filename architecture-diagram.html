Bank Statement Analyzer Architecture

A local-first system that turns a pile of PDF bank statements from many institutions into one reconciled, categorized, traceable financial overview. Deterministic code owns every number; a validation gate stands between parsing and analytics; and every path to the language model runs through a privacy gateway. The model explains figures — it never produces them.

Seven zones, data flowing down

Each zone is one responsibility. Dashed pills are the decision points the design turns on. Red outlines are terminal states — a statement can leave the pipeline here without taking the rest of the batch with it.

Upload failure and validation failure are separate concerns. Invalid files never enter the queue. The queue carries a reference to the stored file, not the PDF bytes.

Temporary File Storage also sits inside this boundary — sensitive data does not leave the controlled processing environment.

Batch Coordinator tracks every job's state and gates aggregation: it begins only once every processable job is terminal. Retries recover transient failures — they do not hide bad input. Max 3 attempts.

4Extraction + Normalization

detect bank + account type + layout version supported w/ confidence?no → UNSUPPORTED / manual review

Native and OCR paths converge on one contract: extracted text. Nothing downstream cares which produced it. Detection identifies bank + account type + layout version — never guess the closest parser, fail loudly. Parsing success is not trustworthy data; validation is the trust gate.

5Trusted Data + Aggregation
Application Data Store all batch jobs terminal? statement-level dedup transaction-level dedup Unified Ledger

Raw PDFs and normalized data live in separate stores. Deduplication is conservative — collapse only on HIGH confidence; keep and flag anything ambiguous. Deleting a real transaction is worse than showing a possible duplicate. The ledger is where the system stops thinking in PDFs and starts thinking in accounts.

6Enrichment + Analytics + AI
merchant normalization rule-based categorization confident?no → Privacy Gateway Local LLM confidence ok?no → Uncategorized
Deterministic Analytics Engine — owns the numbers structured insights (JSON facts) Privacy Gateway Local LLM plain-English explanation

Merchant normalization happens before categorization. Deterministic rules are tried before any model. Categorization degrades to Uncategorized, never a confident guess. User corrections override automation and feed future runs.

7Outputs + Coverage + Cleanup
report builder coverage & data-quality summary — shown first dashboard · report · CSV / JSON export
raw PDF still needed?no → delete raw PDF  always → retain provenance metadata

Incomplete analysis is never presented as complete — excluded statements are listed, not buried. The AI explanation never replaces the metric; the dashboard shows both. Every reported figure stays traceable to account, statement, page, and parser version even after the raw PDF is gone.

02 — Two boundaries the design turns on

The trust gate and the privacy gateway

Everything else follows from these two. They are what make the project more than a PDF parser.

03 — Cross-cutting components

Parts that span the zones

These are not a pipeline stage. They hold state or enforce a rule across the whole flow.

Temporary File Storage

Raw PDFs, only while processing needs them. Sensitive, short-lived, deleted after — unless the user opts to keep them.

Application Data Store

Normalized, non-raw system state: batches, accounts, statements, transactions, validation results, analytics output. Persistent.

Batch Coordinator

Orchestration only, never parses. Tracks per-job state; decides when all processable jobs are terminal; gates aggregation.

Privacy Gateway

Mandatory gate in front of every model call — PII sanitizer plus task-specific payload builder. One component, multiple entry points.

Retry Handling

Separates retryable (transient) from non-retryable (deterministic) failures. Requeue reuses the same temp-file reference. Max 3 attempts.

Coverage / Warning State

Batch-level rollup of what was processed, excluded, and flagged. Surfaced before any numbers.

05 — Invariants

The thirty rules the design commits to

Collected from the design session. Each one is a line the implementation is not allowed to cross.

Intake & queue

  1. Upload failure and validation failure are separate concerns.
  2. One failed statement must not invalidate unrelated statements in the same batch.
  3. Invalid files never enter the processing queue.
  4. Each statement is processed independently; the batch coordinates progress and aggregation.
  5. The queue carries a reference to the temporary file, not the PDF bytes.

Extraction

  1. OCR is a fallback path, not the default extraction method.
  2. Retries recover transient failures — they do not hide bad input (max 3 attempts).
  3. Detect bank + account type + statement format/version from content before parsing; version parsers independently of the bank name.
  4. Never silently guess the closest bank parser — fail loudly.

Canonical boundary & trust

  1. Analytics operates on canonical data, never on bank-specific parser output.
  2. Statements are grouped by account identity, not merely by bank; never silently merge ambiguous accounts.
  3. Parsing success is not trustworthy financial data. Validation is the trust gate.
  4. No statement enters portfolio-level analytics until its normalized data passes minimum validation.
  5. Extraction confidence (fields read correctly?) is separate from validation status (numbers make sense?).
  6. Every normalized transaction remains traceable to its source statement, page, and parser version.

Aggregation

  1. Partial analysis is allowed, but excluded statements must be visible and reflected in report confidence.
  2. Aggregation begins only after every processable statement job has reached a terminal state.
  3. Deduplication is conservative: auto-remove only on HIGH confidence; ambiguous matches kept and flagged.

Analytics & AI

  1. Financial calculations come from deterministic logic; the LLM may explain results but does not own the numbers.
  2. Merchant normalization happens before categorization.
  3. Categorization degrades to Uncategorized, not to a confident guess.
  4. User corrections override automated categorization and feed future categorization.

Privacy

  1. Model location is not the privacy control; sanitization is the privacy control.
  2. Every path into a model passes through the Privacy Gateway. There is no direct path to the model.
  3. The LLM receives the minimum data required for the task.
  4. Raw bank statements are temporary processing artifacts, not permanent application data.

Output

  1. The LLM explanation never replaces the underlying numbers — the dashboard shows both.
  2. Coverage and exclusions are always visible; incomplete datasets are never presented as complete.
  3. Users can export the normalized data — the system is not a closed black box.
  4. Every reported financial fact remains traceable even after raw documents are deleted.

07 — Bonus feature

Household / partner overview

Not part of the MVP. Captured here because it is the feature that would change the project's nature.

vNext · gated

Invite a partner for a joint household view

Combined cash flow, shared-vs-individual spending, household recurring charges, a lender-recognizable household income picture. The catch: it puts one person's financial data in front of another — a direct tension with the local-first thesis — so it does not start until the single-user core ships and is used.

A · Bundle exchange ✓

Each partner keeps their own instance and shares a sanitized, revocable bundle. No server, no shared account, no auth. A small extension of the CSV export.

B · One host

Partner uploads to the host's instance. One live joint view, but asymmetric — the host holds and controls everything. Needs a real invite mechanism.

C · Hosted workspace

Both upload to a shared server. Best UX, natural paid tier — but abandons local-first entirely. A pivot decision, not a bonus feature.

  • The joint view is read-only and derived — the two ledgers are never merged into one owned dataset.
  • Every account and transaction stays attributed to the party that owns it.
  • Sharing is explicit and revocable; the UI says plainly that what is imported cannot be un-copied.
  • Household cash flow nets out inter-party transfers — money moving between partners is not household income or spending.
  • Coverage is reported per party; the joint view is only as complete as the least-covered side.
  • Sharing is always opt-in, never a precondition to using the tool.
